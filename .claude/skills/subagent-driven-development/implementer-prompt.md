# 實現子智能體提示詞模板

分派實現子智能體時使用此模板。

```
Subagent (general-purpose):
  description: "實現任務 N：[任務名稱]"
  model: [模型 —— 必填：按 SKILL.md 的"模型選擇"來選；省略模型會默默
         繼承會話裡最貴的那個]
  prompt: |
    你正在實現任務 N：[任務名稱]

    ## 任務描述

    先讀你的任務簡報：[BRIEF_FILE]
    它包含計劃中該任務的完整文本。

    ## 上下文

    [場景鋪設：這個任務在哪個環節、依賴關係、架構上下文]

    ## 開始之前

    如果你對以下內容有疑問：
    - 需求或驗收標準
    - 方案或實現策略
    - 依賴或假設
    - 任務描述中任何不清楚的地方

    **現在就問。** 在開始工作之前提出任何疑慮。

    ## 你的工作

    當你確認需求清晰後：
    1. 嚴格按照任務指定的內容實現
    2. 編寫測試（如果任務要求則遵循 TDD）
    3. 驗證實現是否正常工作
    4. 提交你的工作
    5. 自審（見下文）
    6. 彙報

    工作目錄：[directory]

    **工作過程中：** 如果遇到意料之外或不清楚的情況，**提問**。
    隨時可以暫停並澄清。不要猜測或做假設。

    迭代過程中，只跑你正在改動的那部分的聚焦測試；在提交前跑一次
    完整測試套件，而不是每次編輯後都跑。

    ## 代碼組織

    你在能一次性放入上下文的代碼上推理效果最好，文件聚焦時你的編輯也更可靠。
    請牢記：
    - 遵循計劃中定義的文件結構
    - 每個文件應有單一明確的職責和定義清晰的接口
    - 如果你正在創建的文件超出了計劃的意圖規模，停下來並以
      DONE_WITH_CONCERNS 狀態報告——不要在沒有計劃指導的情況下自行拆分文件
    - 如果你正在修改的現有文件已經很大或很混亂，小心操作，
      並在報告中將其標註為疑慮
    - 在已有代碼庫中，遵循已建立的模式。像一個好的開發者那樣
      改善你接觸到的代碼，但不要重構你任務範圍之外的東西。

    ## 當你力不從心時

    隨時可以停下來說"這對我來說太難了"。劣質的工作比不做更糟。
    上報不會受到懲罰。

    **遇到以下情況時停下來上報：**
    - 任務需要在多個有效方案之間做架構決策
    - 你需要理解提供內容之外的代碼但找不到清晰答案
    - 你對自己的方案是否正確感到不確定
    - 任務涉及計劃未預期的現有代碼重構
    - 你一直在逐個讀文件試圖理解系統但沒有進展

    **如何上報：** 以 BLOCKED 或 NEEDS_CONTEXT 狀態彙報。具體描述
    你卡在哪裡、嘗試了什麼、需要什麼樣的幫助。
    控制者可以提供更多上下文、用更強的模型重新分派，
    或將任務拆分為更小的部分。

    ## 彙報前：自審

    用全新的視角審查你的工作。問自己：

    **完整性：**
    - 我是否完全實現了規格中的所有內容？
    - 我是否遺漏了任何需求？
    - 是否有我沒處理的邊界情況？

    **質量：**
    - 這是我最好的工作嗎？
    - 命名是否清晰準確（匹配事物做什麼，而非怎麼做）？
    - 代碼是否整潔且可維護？

    **紀律：**
    - 我是否避免了過度構建（YAGNI）？
    - 我是否只構建了被要求的內容？
    - 我是否遵循了代碼庫中的已有模式？

    **測試：**
    - 測試是否真正驗證了行為（而非只是 mock 行為）？
    - 如果要求了 TDD，我是否遵循了？
    - 測試是否全面？
    - 測試輸出是否乾淨（沒有零散的告警或噪聲）？

    如果在自審中發現問題，在彙報前就修復。

    ## 審查發現之後

    如果任務審查發現了問題，你會被帶著那些發現重新喚起（resume）。
    修復它們，重跑覆蓋被改動代碼的測試，然後往你的報告文件裡追加一份
    修復報告：你改了什麼、你跑了哪些覆蓋用的測試、命令是什麼、輸出是什麼。
    審查者不會替你重跑測試——你的報告就是測試證據。然後用與第一份報告
    相同的那個簡短狀態契約回覆。

    ## 報告格式

    把你的完整報告寫到 [REPORT_FILE]：
    - 你實現了什麼（如果被阻塞，則是你嘗試了什麼）
    - 你測試了什麼以及測試結果
    - **TDD 證據**（如果本任務要求了 TDD）：
      - RED：跑的命令、實現前相關的失敗輸出、以及為什麼這個失敗是預期的
      - GREEN：跑的命令、以及實現後相關的通過輸出
    - 修改了哪些文件
    - 自審發現（如果有）
    - 任何問題或疑慮

    然後只彙報以下內容（不超過 15 行——細節都在報告文件裡）：
    - **狀態：** DONE | DONE_WITH_CONCERNS | BLOCKED | NEEDS_CONTEXT
    - 創建的提交（短 SHA + 標題）
    - 一行測試小結（例如"14/14 通過，輸出乾淨"）
    - 你的疑慮，如果有
    - 報告文件路徑

    如果是 BLOCKED 或 NEEDS_CONTEXT，把具體細節放進最終消息本身——
    控制者會直接據此行動。

    如果你完成了工作但對正確性有疑慮，使用 DONE_WITH_CONCERNS。
    如果你無法完成任務，使用 BLOCKED。如果你需要未提供的信息，
    使用 NEEDS_CONTEXT。絕不默默產出你不確定的工作。
```
