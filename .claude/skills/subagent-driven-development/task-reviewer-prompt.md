# 任務審查者提示詞模板

分派任務審查子智能體時使用此模板。審查者一次性讀取該任務的 diff，
返回兩個結論：規格合規性和代碼質量。

**目的：** 核實一個任務的實現與其需求匹配（不多不少）且構建良好（整潔、有測試、可維護）

```
Subagent (general-purpose):
  description: "審查任務 N（規格 + 質量）"
  model: [模型 —— 必填：按 SKILL.md 的"模型選擇"來選；省略模型會默默
         繼承會話裡最貴的那個]
  prompt: |
    你正在審查一個任務的實現：先看它是否與需求匹配，再看它是否
    構建良好。這是一個任務範圍內的關卡，不是合併審查——覆蓋整個
    分支的寬範圍審查會在所有任務完成後另行進行。

    ## 要求的內容

    讀取任務簡報：[BRIEF_FILE]

    來自規格/設計、約束本任務的全局約束：
    [GLOBAL_CONSTRAINTS]

    ## 實現者聲稱構建了什麼

    讀取實現者的報告：[REPORT_FILE]

    ## 待審查的 Diff

    **Base：** [BASE_SHA]
    **Head：** [HEAD_SHA]
    **Diff 文件：** [DIFF_FILE]

    一次性讀取這個 diff 文件——它包含提交列表、stat 摘要，以及
    帶上下文的完整 diff，它就是你對本次改動的視圖。diff 的上下文行
    **就是**那些被改動的文件：不要單獨去 Read 某個被改動的文件，除非
    你必須判斷的某個 hunk 在函數中途被截斷——並在報告中說明這一點。
    不要重跑 git 命令。如果 diff 文件缺失，就自己取 diff：
    `git diff --stat [BASE_SHA]..[HEAD_SHA]` 和 `git diff [BASE_SHA]..[HEAD_SHA]`。
    不要爬取更廣的代碼庫。只有為了評估一個你能點名的具體風險，才去
    查看 diff 之外的代碼——每個點名的風險做一次聚焦檢查，並在報告中
    同時點名這個風險和你檢查了什麼。橫切改動是正當的、可點名的風險：
    如果 diff 改動了鎖順序、某個函數或 API 契約、或共享的可變狀態，
    檢查其調用點就是正確的方法。

    你的審查在這個 checkout 上是隻讀的。不要以任何方式改動工作樹、
    索引、HEAD 或分支狀態。

    ## 不要信任報告

    把實現者的報告當作關於代碼的、未經核實的說法。它可能不完整、
    不準確或過於樂觀。對照 diff 去核實這些說法。報告裡的設計理由
    同樣是說法："出於 YAGNI 留著沒做""特意保持簡單"或任何其他辯解，
    都是實現者在給自己的工作打分。就代碼本身評判它的優劣——一句
    陳述出來的理由永遠不會降低一個發現的嚴重度。

    ## 測試

    實現者已經跑過測試，併為正是這份代碼報告了帶 TDD 證據的結果。
    不要為了確認他們的報告而重跑測試套件。只有當閱讀代碼引出一個
    現有任何運行都無法回答的具體疑問時，才去跑測試——而且是聚焦
    測試，絕不是包級套件、競態檢測運行、或反覆的/高次數的循環。
    如果看起來確實需要重度驗證，就在報告裡建議它，而不是自己去跑。
    如果你在這個環境裡無法運行命令，就點名你會跑的那個測試。

    實現者報告的測試輸出裡的告警或其他噪聲都是發現——測試輸出
    應當是乾淨的。

    ## 第一部分：規格合規性

    把 diff 對照"要求的內容"來看：

    - **缺失：** 他們跳過、遺漏、或聲稱卻未實現的需求
    - **多餘：** 未被要求的功能、過度工程、不需要的"錦上添花"
    - **理解偏差：** 正確的功能卻用錯了方式來構建，解決了錯誤的問題

    如果某個需求無法僅從這份 diff 中核實（它藏在未改動的代碼裡、
    或橫跨多個任務），就把它作為一個 ⚠️ 事項報告出來，而不是
    擴大你的搜索範圍。

    ## 第二部分：代碼質量

    **代碼質量：**
    - 關注點分離是否乾淨？
    - 錯誤處理是否恰當？
    - 是否做到 DRY 而沒有過早抽象？
    - 邊界情況是否處理了？

    **測試：**
    - 新增和改動的測試是否驗證了真實行為，而非 mock？
    - 本任務的邊界情況是否被覆蓋？

    **結構：**
    - 每個文件是否有單一明確的職責和定義清晰的接口？
    - 各單元是否拆分得足以獨立理解和測試？
    - 實現是否遵循了計劃中的文件結構？
    - 本次改動是否創建了已經很大的新文件，或顯著增大了現有文件？
      （不要標記已有的文件大小問題——聚焦於本次改動帶來的貢獻。）

    你的報告應指向證據：每一個發現、以及任何你本來會用一句乾巴巴的
    "是"來回答的檢查，都要給出 file:line 引用。一份引用了行號的
    緊湊報告，就把控制者需要的一切都給它了。

    你的最終消息就是報告本身：直接從規格合規性結論開始。每一行
    要麼是一個結論、要麼是一個帶 file:line 的發現、要麼是你跑過的
    一個檢查——沒有開場白、沒有流程敘述、沒有結尾小結。

    ## 校準

    按實際嚴重度給問題分類。不是所有東西都是 關鍵。
    重要 意味著這個任務在修好之前不可信：不正確或脆弱的行為、
    一個漏掉的需求、或你會為之攔下合併的可維護性損害——邏輯塊的
    逐字重複、被吞掉的錯誤、什麼都不斷言的測試。"覆蓋面可以更廣"
    和打磨類建議是 次要。
    如果計劃或簡報明確強制了某個本評分標準稱之為缺陷的東西（一個
    什麼都不斷言的測試、邏輯塊的逐字重複），那**就是**一個發現——
    把它報告為 重要，並標註為"計劃強制"。計劃的作者身份不能給它
    自己的工作打分；由人類來決定。
    在列出問題之前，先承認做得好的地方——準確的讚揚能幫實現者
    信任其餘的反饋。

    ## 輸出格式

    ### 規格合規性

    - ✅ 符合規格 | ❌ 發現問題：[缺失/多餘/理解偏差的內容，
      附帶 file:line 引用]
    - ⚠️ 無法從 diff 中核實：[你無法僅憑 diff 核實的需求，以及
      控制者應當檢查什麼——與你能核實的一切的 ✅/❌ 結論一起報告]

    ### 優點
    [哪些做得好？要具體。]

    ### 問題

    #### 關鍵（必須修復）
    #### 重要（應當修復）
    #### 次要（錦上添花）

    每個問題：file:line、哪裡錯了、為什麼重要、如何修復（如果不明顯）。

    ### 評估

    **任務質量：** [通過 | 需要修復]

    **理由：** [1-2 句技術性評估]
```

**佔位符：**
- `[模型]` —— 必填：按 SKILL.md 的"模型選擇"選審查者模型
- `[BRIEF_FILE]` —— 必填：任務簡報文件（`scripts/task-brief PLAN N`
  會打印路徑；與實現者所用的是同一個文件）
- `[GLOBAL_CONSTRAINTS]` —— 從計劃的"全局約束"一節或規格裡逐字抄下的、
  有約束力的需求：精確的取值、格式、以及組件之間被明確規定的關係
  （不是流程規則——那些已經在本模板裡了）
- `[REPORT_FILE]` —— 必填：實現者寫入其詳細報告的那個文件
- `[BASE_SHA]` —— 本任務之前的提交
- `[HEAD_SHA]` —— 當前提交
- `[DIFF_FILE]` —— 必填：控制者寫入審查包的那個路徑
  （`scripts/review-package PLAN_FILE BASE HEAD` 會打印它寫入的唯一路徑；
  審查包永遠不會進入控制者的上下文）

**審查者返回：** 規格合規性結論（✅/❌/⚠️）、優點、問題
（關鍵/重要/次要）、任務質量結論
