# 編寫計劃

## 概述

編寫全面的實現計劃，假設工程師對我們的代碼庫零上下文，且品味存疑。記錄他們需要知道的一切：每個任務要修改哪些文件、代碼、測試、可能需要查閱的文檔、如何測試。將整個計劃拆成小步驟任務。DRY。YAGNI。TDD。頻繁 commit。

假設他們是有經驗的開發者，但對我們的工具鏈和問題領域幾乎一無所知。假設他們不太擅長測試設計。

**開始時宣佈：** "我正在使用 writing-plans 技能創建實現計劃。"

**上下文：** 此技能應在專用 worktree 中運行（由 brainstorming 技能創建）。

**計劃保存位置：** `docs/superpowers/plans/YYYY-MM-DD-<feature-name>.md`
- （用戶對計劃位置的偏好優先於此默認值）

## 範圍檢查

如果規格涵蓋了多個獨立子系統，它應該在頭腦風暴階段就被拆分為子項目規格。如果沒有，建議將其拆分為獨立的計劃——每個子系統一個。每個計劃應該能獨立產出可工作、可測試的軟件。

## 文件結構

在定義任務之前，先列出將要創建或修改的文件以及每個文件的職責。這是鎖定分解決策的地方。

- 設計邊界清晰、接口定義良好的單元。每個文件應有一個明確的職責。
- 你對能一次放入上下文的代碼推理得最好，文件越專注你的編輯越可靠。優先選擇小而專注的文件，而非承擔過多功能的大文件。
- 一起變更的文件應放在一起。按職責拆分，而非按技術層級拆分。
- 在現有代碼庫中，遵循已有模式。如果代碼庫使用大文件，不要單方面重構——但如果你正在修改的文件已經變得難以管理，在計劃中包含拆分是合理的。

此結構決定了任務分解。每個任務應產出獨立的、有意義的變更。

## 任務粒度定界

一個任務是**能獨立承載自己那一輪測試循環、且值得一個全新審查者把關**的最小單元。劃任務邊界時：把搭建、配置、腳手架和文檔這些步驟，折進那個真正需要它們的交付物所在的任務裡；只在「審查者有可能否掉這個任務、同時批准它旁邊那個」的地方才拆開。每個任務都以一個**可獨立測試的交付物**結束。

## 小步驟任務粒度

**每步是一個操作（2-5 分鐘）：**
- "編寫失敗的測試" - 一步
- "運行它確認失敗" - 一步
- "實現最少代碼讓測試通過" - 一步
- "運行測試確認通過" - 一步
- "Commit" - 一步

## 計劃文檔頭部

**每個計劃必須以此頭部開始：**

```markdown
# [功能名稱] 實現計劃

> **面向 AI 代理的工作者：** 必需子技能：使用 superpowers:subagent-driven-development（推薦）或 superpowers:executing-plans 逐任務實現此計劃。步驟使用複選框（`- [ ]`）語法來跟蹤進度。

**目標：** [一句話描述要構建什麼]

**架構：** [2-3 句話描述方案]

**技術棧：** [關鍵技術/庫]

---
```

## 任務結構

````markdown
### 任務 N：[組件名稱]

**文件：**
- 創建：`exact/path/to/file.py`
- 修改：`exact/path/to/existing.py:123-145`
- 測試：`tests/exact/path/to/test.py`

- [ ] **步驟 1：編寫失敗的測試**

```python
def test_specific_behavior():
    result = function(input)
    assert result == expected
```

- [ ] **步驟 2：運行測試驗證失敗**

運行：`pytest tests/path/test.py::test_name -v`
預期：FAIL，報錯 "function not defined"

- [ ] **步驟 3：編寫最少實現代碼**

```python
def function(input):
    return expected
```

- [ ] **步驟 4：運行測試驗證通過**

運行：`pytest tests/path/test.py::test_name -v`
預期：PASS

- [ ] **步驟 5：Commit**

```bash
git add tests/path/test.py src/path/file.py
git commit -m "feat: add specific feature"
```
````

## 禁止佔位符

每個步驟都必須包含工程師需要的實際內容。以下是**計劃缺陷**——絕不要寫出來：
- "待定"、"TODO"、"後續實現"、"補充細節"
- "添加適當的錯誤處理" / "添加驗證" / "處理邊界情況"
- "為上述代碼編寫測試"（沒有實際測試代碼）
- "類似任務 N"（重複代碼——工程師可能不按順序閱讀任務）
- 只描述做什麼而不展示怎麼做的步驟（代碼步驟必須有代碼塊）
- 引用了未在任何任務中定義的類型、函數或方法

## 自檢

編寫完整計劃後，以全新視角審視規格並對照檢查計劃。這是你自己執行的檢查清單——不是子代理調度。

**1. 規格覆蓋度：** 瀏覽規格中的每個章節/需求。你能指出實現它的任務嗎？列出所有遺漏。

**2. 佔位符掃描：** 搜索計劃中的紅旗——上方"禁止佔位符"章節中的任何模式。修復它們。

**3. 類型一致性：** 後續任務中使用的類型、方法簽名和屬性名是否與前面任務中定義的一致？任務 3 中叫 `clearLayers()` 但任務 7 中叫 `clearFullLayers()` 就是 bug。

如果發現問題，直接內聯修復。無需重新審查——修好繼續推進。如果發現規格中的需求沒有對應任務，就添加任務。

## 執行交接

保存計劃後，提供執行選項：

**"計劃已完成並保存到 `docs/superpowers/plans/<filename>.md`。兩種執行方式：**

**1. 子代理驅動（推薦）** - 每個任務調度一個新的子代理，任務間進行審查，快速迭代

**2. 內聯執行** - 在當前會話中使用 executing-plans 執行任務，批量執行並設有檢查點

**選哪種方式？"**

**如果選擇子代理驅動：**
- **必需子技能：** 使用 superpowers:subagent-driven-development
- 每個任務一個新子代理 + 兩階段審查

**如果選擇內聯執行：**
- **必需子技能：** 使用 superpowers:executing-plans
- 批量執行並設有檢查點供審查
