# 寫好測試

**在以下情況加載此參考：** 編寫或修改測試、添加 mock、或為測試添加清理/輔助方法時。

## 概述

一個測試的存在是為了抓住某個**具體的**破壞。這裡的一切都由兩條原則統轄：

```
1. 每個測試都點名它要抓的破壞
2. 每個測試都跑真東西
```

嚴格的 TDD 會自然產出這兩點：一個先寫、並且在真實代碼上親眼看著它失敗過的測試，已經證明了自己**能**失敗；而只有當真實依賴被證明緩慢或屬於外部時，mock 才配被引入。

## 原則 1：點名它要抓的破壞

在寫測試體之前，先回答：**什麼樣的生產代碼改動應該讓這個測試失敗——而那個改動是 bug 還是一個決定？** 一個測試靠抓住走錯的分支、缺失的副作用、傳錯的參數、邊界情況或被破壞的契約來贏得它的位置。

**獨立推導期望值。** 用字面量和手工核對過的 fixture；帶字面量 `want` 值的表驅動測試是首選形態。一個由**被測代碼本身**（或它的輔助函數）算出來的期望值，無論那段代碼幹了什麼都會通過：

```typescript
// ❌ 鏡像斷言：同一個 builder 算出了等式兩邊 —— 永遠為真
const expected = buildSearchQuery({ tag: 'urgent' });
expect(buildSearchQuery({ tag: 'urgent' })).toBe(expected);

// ✅ 手工推導的字面量
expect(buildSearchQuery({ tag: 'urgent' })).toBe('tag:"urgent"');
```

**不要寫變更探測器。** 如果只有**有意為之的決定**才能讓一個測試失敗——某個常量的取值、某句消息的精確措辭、某個私有結構——那它會在重新設計時誤報、卻對真 bug 一路沉睡。要測那個**依賴於該決定的行為**：不是 `expect(MAX_RETRIES).toBe(5)`，而是"一次失敗的調用會被重試 5 次，且第 6 次嘗試永不發生"。

**測行為，不測文本。** 斷言某個腳本、skill 或配置文件"包含某一行"，只能證明源文件就是源文件。要拿受控輸入去**跑**腳本，然後斷言它的輸出、副作用或退出碼。用來指揮 agent 的文檔，靠消費它的 agent 的行為來測（superpowers:writing-skills）；寫給人看的散文根本不該有測試。

**測你的代碼，不測框架。** 測你的代碼在其邊界上所做的契約——你註冊的那條路由、你發出的那條查詢、你產出的那個 payload。上游的機制是它們維護者該寫的測試（經典反例：斷言你的 router 會調用一個已註冊的 handler——那是框架的測試，不是你的）。當上遊行為**確實**讓你意外時，寫一個窄窄的表徵測試，把那個假設點名出來。同樣的邊界也適用於你代碼內部：構造函數、getter、常量和瑣碎的轉發，只有當它們做校驗、歸一化、給默認值、做推導、做強制或產生副作用時才配有測試——否則就去斷言第一個依賴於它們、且對消費者可見的結果。

### 門控函數

```
在寫測試體之前：
  點名那個會讓這個測試失敗的生產代碼改動。

  點不出來                    → 圍繞一個可觀察的行為重新設計
  "源文本變了"                → 去跑這個產物，斷言它的效果
  只有有意為之的決定能讓它失敗  → 這是變更探測器；改測那個
                               依賴於該決定的行為

  確認期望值的推導過程沒有用到被測代碼。
  如果它複用了被測代碼的邏輯或輔助函數：
    換成字面量或手工核對過的 fixture
```

## 原則 2：跑真東西

**mock 不配擁有斷言。** 一個針對 mock 的斷言，在 mock 存在時通過、在 mock 缺席時失敗——它對被測組件什麼都沒說。要斷言**真實組件**的行為；如果你要檢查的就是那個 mock，那就把它 unmock，或者把這條斷言刪掉。

```typescript
// ✅ 真實行為
expect(screen.getByRole('navigation')).toBeInTheDocument();

// ❌ mock 是否存在
expect(screen.getByTestId('sidebar-mock')).toBeInTheDocument();
```

**你的人類夥伴會這樣糾正你：** "我們是在測一個 mock 的行為嗎？"

**在正確的層級上 mock。** 在替換真實方法之前，先搞清它的每一個副作用；只 mock 掉慢的或外部的那一步操作，把測試真正依賴的東西保留為真實的。不確定時，先拿真實實現跑一遍測試，觀察實際上必須發生什麼。

```typescript
// ❌ 這個 mock 吞掉了配置寫入，而重複檢測正是要讀它
vi.mock('ToolCatalog', () => ({
  discoverAndCacheTools: vi.fn().mockResolvedValue(undefined)
}));

// ✅ 只 mock 掉緩慢的服務器啟動；配置寫入保持真實
vi.mock('MCPServerManager');
```

**讓替身足夠具體。** 當參數、調用次數或調用順序本身就是契約的一部分時，就要斷言它們——一個什麼都接受的 fake 什麼都沒驗證。給每個分支（成功、報錯、格式錯誤）配它自己的 fixture 或 spy，這樣走錯的分支就無法滿足期望。

**完整鏡像真實數據。** 按現實中的**完整結構**來 mock——所有有文檔的字段——而不是隻 mock 你這個測試會讀的那幾個。部分 mock 會靜默失敗：下游代碼讀到一個被省略的字段時，測試通過、集成崩掉。

**生產類只承載生產方法。** 只有測試才需要的清理邏輯，放在測試工具裡，絕不作為生產類上的 `destroy()`。自問：這個方法只被測試調用嗎？這個類擁有這份資源的生命週期嗎？答錯了 → 挪進測試工具。

**寧可用真實組件，也不要複雜 mock。** 當 mock 的搭建代碼超過測試邏輯本身、mock 漏掉了真實組件才有的方法、或者 mock 一改測試就崩時，改成用真實組件的集成測試。**你的人類夥伴會這樣問：** "這裡我們真的需要用 mock 嗎？"

### 門控函數

```
在添加 mock 或測試輔助函數之前：
  列出真實方法的副作用；測試所依賴的那些保持真實 ——
  只 mock 它們下面那一層「慢的/外部的」。

  mock 的返回值要完整鏡像真實結構。

  只被測試調用的方法，屬於測試工具，不屬於生產代碼。

  正要對 mock 本身下斷言？
    把它 unmock，或者刪掉這條斷言。
```

## 測試與實現一同交付

TDD 循環——失敗的測試、最小實現、重構——就是"完成"的定義。交付這個行為**需要**的測試，且只交付這些：瑣碎代碼和給人看的散文都不配有測試，而一個為了滿足流程而寫的測試會永遠付出維護代價。

## 變異檢查

收尾之前，在腦子裡對生產代碼做變異；對每一種現實的變異，都應至少有一個測試失敗：

- 常量或參數寫錯
- 分支處理寫錯
- 缺失狀態變更或副作用
- 返回空值或默認值
- 缺失對零值、空值、nil、未授權或格式錯誤輸入的校驗

一個沒有任何測試能抓住的變異，標記出該行為無保護——或者那個測試是同義反復。

## 快速參考

| 當你…… | 就這麼做 |
|--------|---------|
| 寫任何測試 | 點名它要抓的破壞——是 bug，不是決定 |
| 構造期望值 | 手工推導；絕不用被測代碼去算 |
| 測一個腳本或文檔 | 跑它 / 壓測它的消費者；絕不 grep 它的文本 |
| 想給依賴寫測試 | 測你的邊界契約，不測它們有文檔的機制 |
| 想對一個被 mock 的元素下斷言 | 改測真實組件，或者把它 unmock |
| 正要 mock 某個方法 | 先搞清它的副作用；在慢的/外部的那一層上 mock |
| 構造一個 mock 返回值 | 完整鏡像真實結構 |
| 需要只有測試才用的清理邏輯 | 放進測試工具 |
| 眼看 mock 搭建代碼膨脹 | 改成用真實組件的集成測試 |
| 寫完一個測試文件 | 跑一遍變異檢查 |

## 危險信號

- 搭建過程和斷言共用同一個對象，等式必然成立
- 這個測試只可能因為 panic、崩潰或選擇器缺失而失敗
- 這個測試在每次有意改動時都失敗，卻從不在意外破壞時失敗
- 期望值藏在循環、builder 或輔助函數背後
- 這個測試去 grep 源碼文本，或者斷言某個已刪除的符號仍然是刪除狀態
- 就算只剩下框架，這個測試依然"成立"
- 這個測試是為覆蓋率而存在的，不檢查任何副作用或結果
- 某條斷言檢查的是 `*-mock` 這種 test ID，或者你把 mock 去掉它就失敗
- 某個方法只被測試文件調用
- mock 搭建佔了測試的一半以上，或者你說不出為什麼需要這個 mock
- "為了安全起見"而 mock
